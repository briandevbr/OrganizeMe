02 · workflow

Cheguei no projeto hoje. O que eu faço?

Siga os passos na ordem e marque cada um quando terminar. Do segundo dia em diante, você pula o passo 1: é só entrar na pasta, conferir a branch e puxar as atualizações.

🧰
Antes de tudo, instale: Git (no Windows ele já traz o Git Bash), VS Code com as extensões Prettier e Live Server (passo a passo em Ferramentas do time), e crie sua conta no GitHub. Mande seu usuário para o David para receber o convite do repositório — sem ele o git push não funciona.

03 · terminal básico

Os 4 comandos para não se perder

O terminal é só outro jeito de navegar pelas pastas, como o Explorador de Arquivos — mas digitando. Com estes quatro você já anda por qualquer lugar.

🪟
Está no Windows? Use o Git Bash (vem junto com o Git): todos os comandos desta página funcionam igual lá. No Prompt de Comando (cmd) alguns nomes mudam — estão indicados abaixo. Para colar no terminal: Ctrl+V no PowerShell/Windows Terminal, Shift+Insert ou botão direito no Git Bash, Ctrl+Shift+V no Linux e ⌘+V no Mac.

04 · fluxo do git

Git do zero ao push

Pense no Git como um correio: add coloca as coisas na caixa, commit fecha a caixa e cola uma etiqueta, push despacha para o GitHub. E o pull é buscar as caixas que os outros mandaram.

📁
Sua pasta
os arquivos que você editou
git add
📦
Área de preparo
o que vai no próximo commit
git commit
🗂️
Histórico local
salvo só no seu computador
git push
☁️
GitHub
o time inteiro enxerga

⟵ git pull traz do GitHub para a sua pasta o que os outros enviaram

0

Apresente-se ao Git só 1 vez por computador

O Git assina cada commit com seu nome e e-mail. Use o mesmo e-mail da sua conta do GitHub. A terceira linha evita um erro chato no git pull.

git config --global user.name "Seu Nome"
git config --global user.email "seu-email@exemplo.com"
git config --global pull.rebase false
1

git clone — baixar o projeto

Cria a pasta OrganizeMe com todo o código e histórico.

Quando: uma única vez, no primeiro dia.

git clone https://github.com/briandevbr/OrganizeMe.git
2

git status — o seu melhor amigo

Diz em qual branch você está e quais arquivos mudaram. Não altera nada, então pode rodar à vontade.

Quando: sempre que bater a dúvida — e antes de todo commit.

git status
On branch Front-End
Changes not staged for commit:
        modified:   front/HTML/login.html
3

git checkout — trocar de branch

Leva você para a branch da sua área. O nome precisa ser exatamente igual, com maiúsculas e hífen.

Quando: logo depois do clone e sempre que git status mostrar a branch errada. Faça commit antes de trocar.

🎨 Esquadrão Front-end

git checkout Front-End

⚙️ Esquadrão Back-end

git checkout backEnd
4

git pull — ficar em dia

Baixa e junta na sua branch o que os colegas enviaram para o GitHub.

Quando: ao começar o dia e logo antes de cada git push.

git pull
5

git add — colocar na caixa

Separa as alterações que vão entrar no próximo commit. O ponto significa "tudo o que mudou nesta pasta".

Quando: depois de conferir o git status. Para um arquivo só, troque o ponto pelo caminho dele.

git add .
git add front/HTML/login.html
6

git commit -m — fechar a caixa com etiqueta

Salva um "ponto de restauração" com uma mensagem no padrão tipo(escopo): descrição. As regras e um gerador de mensagens estão em Commits padronizados.

git commit -m "fix(cadastro): corrige validação do e-mail"
7

git push — despachar para o GitHub

Envia seus commits para a sua branch no GitHub. A partir daqui o time inteiro vê o que você fez.

Quando: depois do commit e de um git pull. Confira no git status se você está na branch certa.

git push

05 · commits padronizados

Mensagens de commit que todo mundo entende

O histórico do Git é o diário do projeto. Se todo mundo escreve no mesmo formato, dá para bater o olho e saber o que mudou e onde. O time segue o padrão Conventional Commits.

feat(login): adiciona botão de mostrar senha
tipo — que tipo de mudança é. Obrigatório.
escopo — onde mudou: a tela ou o módulo. Opcional, entre parênteses.
descrição — o que o commit faz, em poucas palavras.

Tipos que o time usa

feat funcionalidade nova: tela, botão, validação
fix correção de bug
docs documentação, README, comentários
style só formatação (espaços, aspas, Prettier). Não é CSS: mudança visual é feat ou fix
refactor melhora o código sem mudar o que ele faz
chore arrumação: mover arquivos, configs, .gitignore

Regras da descrição

  • Verbo no presente, completando a frase "este commit…": adiciona, corrige, remove, renomeia.
  • Tudo em minúsculas e sem ponto final.
  • Curta: até 72 caracteres na linha inteira.
  • Um commit, um assunto. Mexeu no login e no dashboard? São dois commits.
  • Escopos mais comuns: home login cadastro dashboard senha inventario readme

✕ Evite

  • mudanças
  • teste
  • Update cadastro.js
  • arrumando umas coisas no css

✓ Prefira

  • fix(login): corrige alinhamento do botão entrar
  • feat(dashboard): adiciona botão de remover item
  • docs(readme): atualiza passo a passo de instalação
  • style: formata o projeto com prettier

    06 · ferramentas do time

    Prettier e Live Server: todo mundo no mesmo padrão

    O Prettier formata o código sozinho toda vez que você salva. Assim ninguém discute espaço ou aspas, e o diff do commit mostra só o que mudou de verdade. O Live Server abre as páginas no navegador e recarrega a cada Ctrl+S. As duas são extensões do VS Code.

    ✨

    Prettier – Code formatter

    ID: esbenp.prettier-vscode

    Instalar pelo terminal

    code --install-extension esbenp.prettier-vscode

    Ou no VS Code: Ctrl+Shift+X, busque Prettier - Code formatter (autor: Prettier) e clique em Install.

    📡

    Live Server

    ID: ritwickdey.LiveServer

    Instalar pelo terminal

    code --install-extension ritwickdey.LiveServer

    Ou no VS Code: Ctrl+Shift+X, busque Live Server (autor: Ritwick Dey) e clique em Install.

    💡
    Apareceu code: command not found? No Mac, abra o VS Code, aperte ⌘+Shift+P e rode Shell Command: Install 'code' command in PATH. No Windows, o instalador do VS Code tem a opção Add to PATH. Ou instale pelo painel de extensões, que dá no mesmo.
    1

    Ligue o "formatar ao salvar"

    Abra as configurações com Ctrl+, (no Mac, ⌘+,). Busque format on save e marque a caixa. Depois busque default formatter e escolha Prettier - Code formatter.

    Quando os líderes subirem a configuração do time (abaixo), o VS Code já abre o projeto com isso ligado.

    2

    Abra as telas com o Live Server

    Clique com o botão direito em index.html e escolha Open with Live Server, ou clique em Go Live na barra azul de baixo. O navegador abre o endereço abaixo e recarrega sozinho a cada salvamento.

    http://127.0.0.1:5500/index.html

    Para desligar, clique em Port : 5500 na mesma barra.

    3

    Teste se está funcionando

    Abra qualquer arquivo, bagunce o recuo de algumas linhas e salve. Se o Prettier arrumar sozinho, deu certo. Para formatar sem salvar: Shift+Alt+F no Windows, Shift+Option+F no Mac e Ctrl+Shift+I no Linux.

    🛠️ Para os líderes: deixar o padrão no repositório (só uma vez)

    Com estes arquivos commitados, todo mundo que clonar o projeto recebe as mesmas regras de formatação, e o VS Code sugere instalar as duas extensões.

    1. Crie o .prettierrc na raiz. São os padrões do Prettier 3, e o cadastro.js já segue esse estilo.
      { "semi": true, "singleQuote": false, "tabWidth": 2, "trailingComma": "all", "printWidth": 80 }
    2. Crie o .vscode/settings.json para ligar o formatar ao salvar no projeto:
      { "editor.defaultFormatter": "esbenp.prettier-vscode", "editor.formatOnSave": true }
    3. Crie o .vscode/extensions.json para o VS Code recomendar as extensões ao abrir o projeto:
      { "recommendations": ["esbenp.prettier-vscode", "ritwickdey.LiveServer"] }
    4. Ajuste o .gitignore. Hoje ele ignora a pasta .vscode/ inteira, então os dois arquivos acima não seriam enviados. Troque a linha .vscode/ por:
      .vscode/* !.vscode/settings.json !.vscode/extensions.json
    5. Commite a configuração e dê push na branch:
      git add .
      git commit -m "chore: adiciona configuração do prettier e do vs code"
    6. Formate o projeto inteiro uma vez (precisa do Node.js). Faça isso quando todo mundo já tiver dado push: o comando mexe em muitas linhas e pode gerar conflitos com trabalho pendente.
      npx prettier@3 --write .
      git add .
      git commit -m "style: formata o projeto com prettier"

    07 · regras das branches

    Cada esquadrão na sua branch

    Uma branch é uma "linha do tempo" paralela do projeto. Cada esquadrão trabalha na sua, e o que fica pronto chega na main por Pull Request, revisado pela liderança.

    main 🔒 versão oficial

    A versão estável do projeto. Ninguém faz push direto nela: tudo entra por Pull Request revisado pelos líderes.

    Front-End 🎨 Esquadrão Front · Davi Perrelli

    Telas, estilos e interações no navegador: a pasta front/ e os scripts de tela cad.js e login.js, que hoje ficam em back/codigoFonte/.

    backEnd ⚙️ Esquadrão Back · David Brian

    Servidor, dados e regras de negócio: o que fica na pasta back/.

    1. Confira a branch antes de codar. Rode git status e veja a primeira linha.
    2. Pull antes de começar e antes do push. Evita conflito e push recusado.
    3. Commits pequenos, um assunto por vez, no padrão Conventional Commits: tipo(escopo): descrição.
    4. Mexa só na pasta da sua área. Precisa alterar algo do outro esquadrão? Combine antes com o líder dele.
    5. Nunca faça push direto na main.
    6. Nunca use git push --force — ele pode apagar o trabalho dos colegas.
    7. Nunca suba senhas ou o arquivo .env. O .gitignore já ignora, mas fique de olho.

    08 · deu ruim?

    Erros comuns (e como sair deles)

    Todo mundo passa por esses. Clique no erro que apareceu para ver a solução.

    fatal: not a git repository
    Você está fora da pasta do projeto. Veja onde está e entre nela:
    pwd
    cd OrganizeMe
    error: pathspec '...' did not match any file(s) known to git
    O nome da branch está errado. Maiúsculas importam: Front-End é diferente de front-end. Atualize a lista e veja os nomes exatos:
    git fetch
    git branch -a
    ! [rejected] ... (fetch first) no push
    Alguém enviou antes de você. Puxe as novidades e mande de novo:
    git pull
    git push
    Author identity unknown — Please tell me who you are
    Faltou se apresentar ao Git. Rode o passo 0 da seção Git e tente o commit de novo:
    git config --global user.name "Seu Nome"
    git config --global user.email "seu-email@exemplo.com"
    Abriu uma tela estranha depois do git commit
    Você esqueceu o -m "mensagem" e o Git abriu um editor (geralmente o Vim). Para sair sem salvar, aperte Esc, digite o comando abaixo e dê Enter. Depois refaça o commit com -m.
    :q!
    Your local changes ... would be overwritten by checkout
    Você tem alterações sem commit e tentou trocar de branch. Faça o commit primeiro (ou peça ajuda ao seu líder se não quiser guardar essas mudanças):
    git add .
    git commit -m "feat(login): salva progresso da validação"
    CONFLICT (content): Merge conflict in ...
    Você e um colega mexeram na mesma linha. Calma, nada foi perdido. Abra o arquivo no VS Code: ele mostra as duas versões com os botões Accept Current / Accept Incoming / Accept Both. Na dúvida sobre qual manter, chame o líder do seu esquadrão antes de decidir. Depois de resolver:
    git add .
    git commit -m "fix: resolve conflito de merge"
